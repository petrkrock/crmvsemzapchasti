# V1 WORKING (v1.6.4) — исправление потери данных при F5

## Что исправлено относительно V1 PRODUCTION_HARDENED
В `src/lib/store.ts` функция `initRemoteSync()`:
- Раньше: сначала стирался localStorage-кэш, потом pull. Ошибка pull (offline/RLS/сессия)
  или пустой сервер → локальные данные уничтожались при каждой перезагрузке (F5).
- Теперь:
  1) pull выполняется ПЕРВЫМ; при неудаче локальные данные НЕ трогаются;
  2) сервер пуст + локально есть записи → локаль принимается за истину и выгружается
     на сервер (pushRemoteDiff создаст все строки), с проверкой владельца по email сессии —
     защита CRITICAL-03 от выгрузки чужого кэша сохранена;
  3) сервер с данными → он источник истины, кэш чистится после успешного pull.

## Важно про уже потерянные данные
Если после прошлых F5 localStorage очищен И сервер пуст — данные не восстановятся
(см. бэкапы: CSV-экспорты и бэкап БД). Если данные на сервере есть — F5 подтянет их обратно.

## Проверка после установки
1. npm install && npm run build
2. npm run dev → создать поставщика → F5 → данные на месте
3. F5 с выключенной сетью → данные на месте
4. Две вкладки → изменения видны в обеих

## HOTFIX 1.6.5 — F5 в demo-режиме и пустой сервер
- Демо-режим (VITE_DEMO_MODE=true): синхронизация полностью отключена — localStorage единственный источник, F5 больше не может ничего стереть.

- Ветка «сервер полностью пуст»: пуш всех локальных строк реально выполняется.

## HOTFIX 1.6.6 — КОРЕНЬ потери данных при F5 (demo и не только)
Причина: getStore() в V1 выполняет цепочку миграций внутри try, а catch писал
defaultStore() прямо в localStorage. Любая миграция, бросавшая TypeError на форме
данных (например mediaAdTypes не-массив), МОЛЧА СТИРАЛА ВСЮ БАЗУ при загрузке.
- catch: FAIL-SAFE — логирует ошибку, возвращает сырые данные как есть, localStorage НЕ трогает.
- mediaAdTypes: гвард Array.isArray.
- clearLocalStoreCache: forensic-лог со стеком (при повторной потере покажет виновника).

## v1.7.6 — «Архив дублей» и «АРХИВ» в статусах лидов (корень)
Причина: ensureSystemStatuses() проверял «уже есть статус?» по id ИЛИ имени.
«Архив дублей»/«АРХИВ» уже существуют для поставщиков/покупателей → совпадение по
имени → лиды-версии молча пропускались → статусы отсутствовали в фильтрах, форме,
массовой смене и настройках лидов.
Теперь: существующий статус РАСШИРЯЕТСЯ entityTypes += 'lead' (общий системный статус
на все три раздела), отсутствующий — создаётся.
